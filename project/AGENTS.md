# Working agreement for agents (forethought)

This project uses forethought, a plan-first workflow. It works the same for every agent and for people. The tool is `python -m forethought` (written `forethought` below).

## Start of every session
1. Run `forethought status`. It says which branch you are on, which change it belongs to, what else is open, and whether knowledge sits on a branch that is not on the base branch yet. If something you need is elsewhere, say so before you start.
2. Read `GOALS.md` (objectives, current milestone, non-goals). If it still has `TODO:` placeholders, the project has no foundation yet: run the kickoff interview (`forethought/playbooks/kickoff.md`) before anything else. At a milestone, run `forethought/playbooks/milestone.md`. For orientation, read `docs/map.md` and the README of the feature folder you will work in, not the whole codebase.
3. Work on one change at a time: the one the human names, or the next open one.

## Rules
1. **No code without an approved plan.** Every piece of work is a change in `changes/<id>/`. Follow `forethought/playbooks/plan.md`. Quick tier is only for trivial fixes.
2. **Only the human approves.** Never run `forethought approve`, for any tier. When a plan is ready, say so and stop. Quick tier skips the critique and review, not the approval. Epics carry no code: build in their child changes. Never commit code to the base branch.
   An approved plan is a contract. To change it, run `forethought revise <id>` and take it through critique and approval again; never edit it in place.
3. **Stay inside the plan.** Touch only the plan's `areas`. If the work needs something outside them, or a new idea comes up, stop: `forethought park "<idea>" --from <id>` and carry on, or tell the human the plan needs to change. Do not quietly expand scope.
4. **Respect the timebox.** If it runs out, stop and report what is done, what is left, and whether to re-plan.
5. **Done means every criterion passes,** with the named test actually run and its result seen. Update each criterion's `status` in the plan to `pass` or `fail` only from real test output.
6. **Data model first.** Changes to entities, relationships or invariants update `docs/data-model.md` in the same change.
7. **Record lessons when they happen.** Something surprised you, broke, or took a wrong turn: `forethought learn "<title>" --area <areas> --body "<what happened; what to do next time>"`. Before planning, search them: `forethought recall <terms>`. Add `--general` only when the lesson is about how to work in any project, not about this one.
8. **Never change the rules.** forethought's own files (`forethought/`, `.claude/`, `.github/`, `.gitignore`) are governance. Never edit them, and never run `forethought allow-governance`. If a rule is in the way, say so and let the human decide.
9. **Knowledge lives on the base branch; code lives on change branches.** Plans, approvals, lessons, parked ideas, research decisions and docs are committed to the base branch. Only code waits on a branch. Never leave a lesson or decision only on a branch: `forethought rescue <id>` brings it home.

## Where things go
| What | Where | Notes |
|---|---|---|
| A feature's code | its own folder, e.g. `src/features/<name>/` | One feature, one folder, one README (`forethought feature <dir>`). Plans name these folders as `areas`. |
| Code shared by two or more features | `src/core/` (or your stack's equivalent) | Only once a second feature actually needs it. |
| Tests | next to the code they test, or `tests/` mirroring it | Name tests after the criterion they prove. |
| A unit of work | `changes/<id>/` | Plan, critique, review, PR description. Created by `forethought new`. |
| Objectives, milestone, non-goals | `GOALS.md` | |
| Status of all work, parking lot | `ROADMAP.md` | Generated table; parking lot via `forethought park`. |
| Lessons | `LESSONS.md` | Via `forethought learn`. Project-specific by default. |
| Data model: entities, relationships, invariants | `docs/data-model.md` | Updated in the same change as the schema. |
| Architectural decisions | `docs/decisions/NNN-title.md` | One short file per decision: context, decision, consequences. |
| Research | `research/<topic>/` | Starts with `forethought research "<topic>"`; ends with a decision in `decision.md`. |
| Overview of the project | `docs/map.md` | Generated by `forethought map`; never edit it by hand. |
| Scratch, experiments, throwaway output | outside the repo | Not in the project tree. |

New kinds of things get a row here before they get a folder.

## Building and finishing a change
1. `forethought start <id>`, then work on branch `change/<id>`. At most a few changes run at once (`max_in_progress`); the pre-commit gate (and CI) refuse code with no started change and flag files outside the plan's `areas`.
2. Build in small steps. Run the named tests; mark each criterion `pass`/`fail` from real output.
3. Get a fresh code review: `forethought review <id>` (or `--print` for a fresh session; reply saved as `changes/<id>/review.md`). Fix every FAIL and review again; a review only counts for the exact code it saw.
4. Record what the change taught you: `forethought learn ...` (or decide there was nothing and say why at finish).
5. `forethought finish <id>`. It writes `changes/<id>/pr.md`; use it as the PR description. Commit the change folder with the code. After the merge, `forethought branches --prune` cleans up.

## Keeping order as the project grows
- `forethought tidy` (weekly or at each milestone) lists what is drifting: feature folders without a README, code no plan ever claimed, research without a decision, stale parked ideas and changes, repeated lessons, branches needing a decision.
- A lesson that keeps coming back becomes a check (test, lint rule, hook): then `forethought enforce <L-n> "<check>"`.
- `forethought map` after structural changes, so `docs/map.md` stays true.
